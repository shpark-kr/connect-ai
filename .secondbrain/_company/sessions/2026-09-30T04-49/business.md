## 🛡️ MiniFunnel Premium 결제 모듈 V&V 최종 검증 체크리스트
*(작성 목적: 시스템의 기술적 안정성을 넘어, 고객이 느끼는 재무적 신뢰와 전문성을 확보)*

### I. 핵심 비즈니스 로직 (Critical Business Logic) 검증 시나리오

| ID | 검증 항목 | 세부 시나리오 및 조건 | 성공 기준 (Acceptance Criteria) |
| :--- | :--- | :--- | :--- |
| **B-01** | **성공적인 결제 흐름** | 1. 신규 가입자(월간/연간 선택)가 결제를 완료했을 때, 청구 내역과 남은 유효 기간이 정확히 표시되어야 한다. <br>2. 첫 달 구독료 외에 추가 결제가 발생하지 않아야 한다 (예: 세금 포함 여부 명확화). | 최종 사용자에게 보여지는 '결제 성공 보고서'가 Deep Navy/Crisis Red 톤의 시스템 로그처럼 전문적이어야 하며, 청구 금액과 시작일/종료일이 정확해야 함. |
| **B-02** | **자동 갱신 로직 (MRR)** | 구독 만료 D-7일 경고 후, 자동 결제에 성공했을 때의 처리 흐름을 검증한다. 실패 시 즉각적인 재시도 메커니즘이 작동해야 한다. | 결제 실패가 발생하면, 시스템은 사용자에게 '만료 임박' 상태를 명확히 알리고, 다음 액션(카드 업데이트/재결제)을 안내하는 페이지로 유도해야 함. (단순 오류 메시지 금지). |
| **B-03** | **프로비저닝 및 권위성 유지** | 결제 성공 후, 고객에게 제공되는 'Premium Funnel Access Token' 또는 유사 자원이 즉시 발급되어야 한다. 이 과정에서 시스템 지연이 발생해서는 안 된다. | 결제 완료 시점과 동시에 유료 기능 접근(API 호출 가능) 여부가 즉각적으로 전환됨을 사용자 경험으로 입증해야 함. (지연 허용 시간: 1초 이내). |

### II. 실패 및 예외 처리 로직 (Resilience & Failure Handling) 검증 시나리오

| ID | 검증 항목 | 세부 시나리오 및 조건 | 성공 기준 (Acceptance Criteria) |
| :--- | :--- | :--- | :--- |
| **F-01** | **재시도 로직 (Retry Mechanism)** | 1. *Card Decline:* 첫 번째 결제 시도가 카드 거절로 실패한다. <br>2. 시스템은 3시간 간격으로 자동 재시도를 2회까지 수행해야 한다. <br>3. 두 번째와 세 번째 재시도 모두 실패할 경우, 최종적으로 사용자에게 **'최대 오류 코드 (Max Error Code)'**를 제공하며, 결제 수단 변경을 유도하는 페이지로 이동해야 한다. | 단순 "결제가 실패했습니다" 메시지가 아닌, `[ERROR: PAYMENT_GATEWAY_FAILURE - CODE 402]`와 같은 전문적이고 구체적인 시스템 에러 코드를 제시해야 하며, 재시도 시점과 남은 재시도를 명확히 알려야 함. |
| **F-02** | **연결 끊김 (Network Interruption)** | 결제 API 호출 도중 네트워크 연결이 불안정하여 세션 중간에 데이터가 유실되는 상황을 가정한다. | 시스템은 트랜잭션의 상태를 'Pending'으로 설정하고, 백그라운드에서 재동기화(Reconciliation) 로직을 실행해야 한다. 사용자에게는 "처리 중입니다. 잠시만 기다려 주십시오."라는 명확한 메시지를 제공해야 함. (데이터 일관성 유지). |
| **F-03** | **사용자 무효화/탈퇴** | 사용자가 시스템 내에서 강제로 계정을 '비활성화'하거나 '탈퇴' 버튼을 눌렀을 때, 미납된 구독료가 있는지 여부와 관계없이 결제 모듈이 즉시 비활성화되어야 한다. | 모든 결제 API 호출 및 리소싱 기능이 해당 유저 ID에 대해 0 권한으로 처리됨을 백엔드에서 검증해야 하며, 이탈 과정도 '프로토콜 종료'처럼 느껴지게 디자인해야 함. |

### III. 상태 전환 및 시간 관리 (State Transition & Time Management) 검증 시나리오

| ID | 검증 항목 | 세부 시나리오 및 조건 | 성공 기준 (Acceptance Criteria) |
| :--- | :--- | :--- | :--- |
| **S-01** | **플랜 업그레이드 (월 → 연)** | 1. 현재 월간 플랜(MiniFunnel Basic)을 사용하던 고객이 만료일 전에 'Premium Funnel'로 업그레이드한다. <br>2. 시스템은 남은 기간에 대한 정밀한 **프로라타스 크레딧(Pro-rata Credit)** 계산을 통해 추가 금액을 산출해야 한다. | 사용자에게 "남은 기간 X개월분 크레딧 반영, 차액 Y원 결제"라는 명확하고 재무적으로 완벽하게 검증된 청구 내역을 보여주어야 함. (이 과정에서 오류가 발생하면 권위성이 급락함). |
| **S-02** | **플랜 다운그레이드 (연 → 월)** | 연간 플랜을 사용하던 고객이 의도적으로 저렴한 월간 플랜으로 전환하려고 할 때의 로직 검증. | 시스템은 '다운그레이드로 인한 기능 제한' 및 '남은 기간의 환불/크레딧 처리 방안'에 대해 명확히 경고하며, 이탈을 막는 강력한 설득성 메시지를 제공해야 한다. (비즈니스 관점: 다운그레이드 억제). |
| **S-03** | **만료일 전후 상태 변화** | 구독 만료일의 자정(Midnight)에 시스템이 정상적으로 'Active' $\rightarrow$ 'Expired'로, 그리고 재결제 성공 시 'Expired' $\rightarrow$ 'Active'로 전환되는 시간을 초 단위로 검증한다. | 시간대(Timezone) 설정을 포함하여 모든 상태 변화가 명확한 로그와 UI 업데이트를 통해 사용자에게 투명하게 전달되어야 한다. (시간적 오류는 신뢰도의 치명타). |
